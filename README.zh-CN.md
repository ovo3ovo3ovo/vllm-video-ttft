# vllm-video-ttft

vLLM 0.31.0 的插件：缩短**视频请求的首字等待**（time to first token）。在解码、缩放切块、视觉塔这几步上做改动；不占 GPU 的那四项（`exact` 预设），送进视觉塔的输入和 vLLM 原生逐位相同。

```bash
pip install -e .                                                   # 1. 装（vLLM 0.31.0 环境里）
python -m vllm_video_ttft.probe --model /path/to/model --tp 1       # 2. 看本机能开什么、推荐参数
VLLM_VIDEO_TTFT_PRESET=exact vllm serve /path/to/model --mm-processor-cache-gb 0   # 3. 起服务
```

---

## 给部署 agent 看：按这四步做

1. **跑 probe**：`python -m vllm_video_ttft.probe --model 模型目录 --tp 计划的TP大小`。只读，几秒跑完，输出 JSON，里面有本机核数、NUMA 分布、内存、`/dev/shm`、每张 GPU 的型号/显存/计算能力、各软件版本、模型属于哪个系列，以及每个插件能不能开、为什么，还有一套推荐的环境变量和启动参数。
2. **对照下面三张表定方案**：[按模型选插件](#按模型选插件)、[按机器选参数](#按机器选参数)、[插件一览](#插件一览)。probe 的推荐值就是按这几节的规则算出来的；表里写着"推断"的地方，要以第 3 步的实测为准。
3. **跑 selfcheck**：`python -m vllm_video_ttft.selfcheck --model 模型目录 视频1 视频2 视频3`。离线比较开插件和不开插件时，送进视觉塔的东西是否逐位相同、每个插件是否真的生效。全部 PASS 再上线。视频建议 1 段短片、2 段 5 分钟以上的长片。
4. **起服务**：把 probe 给的环境变量和参数加上去。日志里会有一行 `vllm_video_ttft 0.1.0: preset=..., on: ...`，写着实际开了哪些。

不确定的时候，用 `exact` 预设：它不改输出，最坏情况是没提速。

## 插件一览

| 插件 | 开关 | 省的是哪一步 | 适用模型 | 改不改输出 | 代价 |
|---|---|---|---|---|---|
| 切段并行解码 | `M2_SEG_DECODE=1` | 解码：按关键帧把一段视频切成多段，用进程池并行解 | 通用：凡是走 vLLM 默认 OpenCV 解码的都行 | 不改（逐位相同） | 进程池常驻内存中位 0.85–1.0 GiB、最多 2.6 GiB；切段请求平均约 31 CPU 核秒（含热身），按长度 12–57 |
| 跳过非参考帧 | `M2_SEG_SKIP_NONREF=1` | 解码：没被抽中、也不被别的帧参考的帧不解 | 同上，叠在切段解码上 | 不改 | 总耗时持平（只有 I/P 帧的长片，帧表那一步多 0.03–0.05 s，被波动盖住）；只对含 B 帧或非参考帧的视频有用 |
| 去掉缩放切块里多余的拷贝 | `M2_COPYFREE_RESIZE=1` | 缩放切块 | 只限 Qwen3-VL 系 | 不改 | 无 |
| 边解码边缩放 | `M2_PIPE_RESIZE=1` | 缩放切块和解码重叠 | 只限 Qwen3-VL 系；要求 `--mm-processor-cache-gb 0` | 不改 | 多一个缩放线程 |
| 视觉塔分块叠进流水线 | `M2_VISION_CHUNK=1` | 视觉塔和解码、缩放重叠，在 API 进程里算 | 只限 Qwen3-VL 系；依赖边解码边缩放 | **改**：视觉塔输出不逐位相同（和每卡一整份比，100 段里 34 段逐位相同，其余 66 段相对差中位 2.9%、最大 6.25%） | 一张卡上多放一份视觉塔（Qwen3.8 实测最多 3.0 GiB） |

**预设**：`VLLM_VIDEO_TTFT_PRESET`
- `off`（默认）：装了也什么都不做。
- `exact`：前四项（切段解码、跳帧、去拷贝、边解码边缩放），输出和 vLLM 逐位相同。
- `all`：再加视觉塔分块。

单个开关的显式设置优先于预设，比如 `VLLM_VIDEO_TTFT_PRESET=exact M2_PIPE_RESIZE=0`。

`M2_STRICT=1` 是测试和自检用的：插件该生效却没生效时直接报错，不悄悄退回 vLLM 原路径。生产环境不要开。

## 按模型选插件

### 每个插件挂在哪（读代码确认，vLLM 0.31.0 / transformers 5.17.0）

- **切段解码、跳帧**：替换 `vllm.multimodal.video_decoders.opencv.decode_opencv` 和 `VideoMediaIO.load_file`。只有最后走到 `decode_video(backend="opencv")` → `decode_opencv` 的视频后端才会被接管。
- **去拷贝**：替换 `transformers` 的 `Qwen3VLVideoProcessor._prepare_input_videos / _preprocess`。
- **边解码边缩放**：替换 `Qwen3VLVideoProcessor.preprocess`、`VideoMediaIO.load_bytes`、`MediaConnector.load_from_url(_async)`、OpenCV 读帧，以及聊天解析里的 `parse_video`。
- **视觉塔分块**：在 API 进程里建一份 vLLM 自己的 `Qwen3_VisionTransformer`，替换 `Qwen3VLMultiModalProcessor._apply_hf_processor_main`，把 `pixel_values_videos` 换成 `video_embeds`。

| 模型系列 | 架构名（config.json） | 例子 | 切段解码 + 跳帧 | 去拷贝 / 边解码边缩放 | 视觉塔分块 | 依据 |

| InternVL | `InternVLChatModel` 等 | OpenGVLab/InternVL3-8B | 能开 | 不生效 | 不生效 | 同上 |

"不生效"的意思是：挂点在这个模型上根本不会被调用，或者插件判断不该接管、自己让路。服务照常跑，不需要特意关掉；只有加了 `M2_STRICT=1` 才会报错。

### 什么时候别开

| 情况 | 别开哪个 | 为什么 |
|---|---|---|
| 要求输出和 vLLM 逐位相同 | 视觉塔分块 | 它让视觉塔输出不再逐位相同（和每卡一整份比，100 段里 34 段逐位相同，其余 66 段相对差中位 2.9%、最大 6.25%，不只是末位舍入）。考题上没看到精度下降，见[精度（会改输出的两项）](#精度会改输出的两项) |
| 开了视频剪枝（`--video-pruning-rate > 0`，EVS / VidCom2） | 视觉塔分块 | 剪枝要看完整段视频才决定保留哪些 token，分块就不等价了；插件会拒绝分块，交回 worker 自己的视觉塔 |
| 一个请求里有多段视频 | 视觉塔分块 | 不支持，自动交回 worker |
| 开着处理器缓存（`--mm-processor-cache-gb > 0`） | 边解码边缩放、视觉塔分块 | 缓存命中时不会重新解码，流水线插件会让路。我们的测量都是 `--mm-processor-cache-gb 0` |
| 换了解码后端（`--media-io-kwargs '{"video":{"backend":"pynvvideocodec"或"torchcodec"}}'`） | 切段解码、跳帧，以及依赖它的流水线 | 切段解码只接管 OpenCV 路径；换了后端就接管不到 |
| `frame_recovery=True` | 切段解码 | vLLM 的坏帧恢复扫描没有重新实现，自动走原路径 |
| 高并发、CPU 吃紧 | 切段解码要谨慎 | 切段请求平均约 31 CPU 核秒（按长度 12–57），常驻内存最多 2.6 GiB；只测过 4/8 并发下结果逐位相同，没测过高并发吞吐，见[高并发](#高并发推断未测) |
| 显存没有余量的卡 | 视觉塔分块 | 要多放一份视觉塔；放不下时插件会报 OOM 并交回 worker（严格模式下报错） |
| 视频都很短（原始帧数 < `M2_SEG_MIN_SRC_FRAMES`，默认 2642） | 切段解码开着也没用 | 短片不切段；短片首字等待的大头在预填充，插件省得少 |

### 插件不生效时会怎样（读代码确认）

- 每种不生效的原因，在日志里只打一次 warning（例如 `m2_seg_decode: using vLLM's decoder (...)`、`m2_pipe_resize: not using the pipelined result (...)`、`m2_vision_chunk: not served (...)`），然后走 vLLM 原来的路径，结果和没装插件一样。
- vLLM 或 transformers 版本不对：插件打一行 warning，不注册（严格模式下启动报错）。
- 模型不是 Qwen3-VL 系：去拷贝和视觉塔分块的挂点根本不会被调用；边解码边缩放在第一次请求时用一次试跑发现拿不到 Qwen3-VL 的处理参数，记住这次失败，以后直接让路，日志只打一行 `not using the pipelined result (...)`。实测（Gemma-4-E2B、LLaVA-OneVision，CPU，各 3 段视频 × 2 次）：试跑只在第一个请求做 1 次，之后 0 次；没有异常，不卡住。
- 非 Qwen3-VL 模型上开 `M2_STRICT=1` 并打开边解码边缩放（比如 `all` 预设），每个请求都会报 `M2StrictError: m2_pipe_resize: could not compute this request's processor kwargs ...`，不会悄悄算错。原因是严格模式把"开了却没生效"一律当错误，不区分"这个模型不适用"和"出了错"：去拷贝和视觉塔分块在非 Qwen 模型上挂点根本不会被调用，所以不报；边解码边缩放要先试跑一次才知道不适用，所以报。因此严格模式只在 Qwen3-VL 上用来自检；非 Qwen 模型只开切段解码 + 跳帧（probe 给的推荐就是这样），不开严格模式时边解码边缩放会自己让路，结果和不装插件一样（已实测 6/6）。

## 按机器选参数

这一节写的是通用规律，部署方按自己机器的核数和 NUMA 布局自己算。数字都来自一台机器：2 路 Xeon Platinum 8558，96 个物理核、192 个逻辑核，4 个 NUMA 节点；8×RTX 5090，TEP8。凡是写"推断"的，都是从这台机器外推的，要用 selfcheck 的耗时确认。

### CPU：线程花在哪

一个视频请求在 API 进程这一侧同时用到三份线程：

| 谁 | 线程数 | 什么时候 |
|---|---|---|
| 切段解码的进程池 | `M2_SEG_N × M2_SEG_THREADS`（默认 16 × 4 = 64） | 只在切段的长视频上 |
| 缩放切块 | `OMP_NUM_THREADS`；开了边解码边缩放以后，和解码同时跑 | 每个视频 |
| vLLM 调度进程 + API 主线程 | 约 1–2 个核 | 一直在 |

解码线程可以超订：实测 64 个解码线程配 48 个逻辑核最快（32 段不再变快）；按下面的公式取，别再往上加。服务里用的 16 × 4 个解码线程加 `OMP_NUM_THREADS=12`，一共 76 个线程（连调度进程和 API 主线程约 78 个），也超过了它所在两个节点的 48 个物理核，这组是在服务里实测过的。段数扫描是在一个 NUMA 节点上做的（24 个物理核、48 个逻辑核），64 个解码线程（16 段 × 4 线程）是那组扫描里最快的；服务里用两个节点（48 个物理核、96 个逻辑核），只跑过 16 × 4 这一组，没再扫。

### CPU：怎么分配

1. **先把核按 NUMA 节点和 socket 划清楚**：`lscpu`，或者看 probe 输出里的 `numa_nodes`。
2. **API 进程、切段进程池、帧缓冲放在同一个 socket 上**：
   - API 进程：`numactl --cpunodebind=N --membind=N vllm serve ...`。
   - 进程池：`M2_SEG_WNODES=N[,同 socket 的另一个节点]`，或者直接写核号 `M2_SEG_WCPUS=...`。
   - 帧缓冲跟着服务的 `--membind` 走。
   - 实测：离线把主进程钉到另一个 socket，35 分钟原片的帧拷回从 1.06 s 涨到 1.72 s，vLLM 原解码从 7.10 s 涨到 8.27 s。服务里用不拷贝的方式时，钉错的代价小得多，只有缩放切块慢 6–10%，但仍然建议钉在同一个 socket。
   - 不设 `M2_SEG_WNODES` / `M2_SEG_WCPUS` 时，本插件默认用本进程允许用的全部核。
3. **段数和每段线程数怎么取舍**（实测，离线，同一台机器，只用一个 NUMA 节点：24 个物理核、48 个逻辑核）：

   | 视频（原始帧数） | vLLM 原解码 | 每段 1 线程：8 段 / 16 段 / 32 段 | 每段 4 线程：8 段 / 16 段 / 32 段 |
   |---|---|---|---|
   | 2642 帧 | 0.637 s | 0.758 / 0.490 / 0.497 | 0.350 / **0.295** / 0.362 |
   | 9156 帧 | 1.316 s | 1.169 / 0.704 / 0.684 | 0.643 / **0.506** / 0.612 |
   | 49715 帧 | 7.411 s | 7.656 / 4.432 / 3.443 | 3.881 / **2.881** / 2.897 |

   - 每段 4 线程、16 段最好；32 段不再变快。
   - 每段 1 线程时，切 8 段有一段已经比原解码快，另两段要 16 段才快。核少的机器上，每段 1 线程、段数多一点，可能比每段 4 线程划算（推断）。
   - FFmpeg 自己的多线程已经开着：vLLM 原解码默认就是多线程，强制 1 线程会慢 6–8 倍。所以核少的机器上，切段解码的收益会明显小于下面结果表里的数（推断）。
4. **缩放切块线程数（`OMP_NUM_THREADS`）**：从 1 线程改成 12 线程，缩放切块降到原来的 0.36–0.46，省的几乎都在"转张量"那一步。不设时 vLLM 会把 API 进程降到 1 线程，所以一定要设。超过 12 线程有没有收益，我们没测。
5. **只调缩放切块的线程数（`M2_PIPE_RESIZE_THREADS`，开了边解码边缩放时才有用）**：不设时用 `OMP_NUM_THREADS`。实测（离线，15 段视频，和不设交替 3 遍）：4 线程以上各档，原片只差 1–3%，短片差 5–8%（只有几毫秒）；2 线程慢 2–6%，1 线程慢 5–20%。变慢的是解码那一段，里面包含和解码重叠进行的缩放，不是解码本身变慢。设了这个开关时，串行（五档、全量 908 段两遍）和 4/8 并发都和不设逐位相同，线程数只作用于本请求。

### CPU：经验公式（probe 用的就是这个）

```text
C_node = API 所在 socket 上能用的节点（4 节点的机器取前两个，2 节点取 1 个，单路取全部）
L = 这些节点的逻辑核数 − 当前 1 分钟负载
P = 这些节点的物理核数 − 当前 1 分钟负载

OMP_NUM_THREADS = clamp(P / 4, 1, 12)
D               = min(64, 4·L / 3)                # 切段解码的线程总数
M2_SEG_THREADS  = 4 if D ≥ 16 else 1
M2_SEG_N        = clamp(D / M2_SEG_THREADS, 2, 16)
M2_SEG_WNODES   = C_node
```

- 实测依据：`D = 4·L / 3` 来自段数扫描那一组条件（一个 NUMA 节点，L = 48 个逻辑核）下最快的 64 个线程（16 段 × 4 线程）；32 段不再变快，所以上限取 64。`OMP_NUM_THREADS` 只测过 1 对 12。
- 外推：在两个节点（L = 96）上，公式也给出 16 × 4（上限封顶），服务里用的就是这组，但没在 96 核上扫别的组合；核比 48 少的机器上算出的值，以及比例 1/4、4/3 本身，都没在别的核数上测过。核少的机器请用 selfcheck 打印的耗时比较两三组设置。

### CPU：切段门槛

- `M2_SEG_MIN_SRC_FRAMES`（默认 2642）：解码要抓的原始帧数达到这个值才切段。原始帧数 = 时长 × 原视频帧率。
- 这个值是在 48 个物理核上定的：我们 100 段测速视频里，2642 帧以上的每段都是切段更快；以下有快有慢（门槛以下 5 段原片：1479 帧慢 0.015 s、2006 帧慢 0.085 s，1153 帧快 0.045 s、1500 帧快 0.008 s、1838 帧快 0.175 s），70 段短片全都更慢。2642 是"在它以上每段都更快"的最小值，不是快慢的交叉点。
- 核少的机器上，切段的固定开销占比更大，交叉点会往上移（推断）。判断方法：拿两三段原始帧数在门槛附近的视频跑 selfcheck，比较 `off` 和 `exact` 两行的秒数；切了反而慢，就把门槛往上调。selfcheck 每种设置只跑一次，看的是方向，不是精确值。

### GPU：单卡和多卡分开看

| 设置 | 单卡（TP=1） | 多卡（TP>1） |
|---|---|---|
| `--mm-encoder-tp-mode data` | 开不开都一样 | 建议开：每张卡放一整份视觉塔，不用跨卡切分。代价是每张卡多占一份视觉塔的显存；它会改视觉塔输出，精度见[精度（会改输出的两项）](#精度会改输出的两项) |
| `VLLM_MQ_MAX_CHUNK_BYTES_MB` | **别设**：只有一个 worker 时，vLLM 不用多进程执行器（`vllm/config/parallel.py:1033` 选 uni 执行器），而这条广播环只在多进程执行器里按这个值建（`vllm/v1/executor/multiproc_executor.py:151`） | 建议设成大于单条请求里最大的那份消息：不开视觉塔分块时发的是像素（我们的原片 106–142 MiB），开了以后发的是视觉特征（我们的 100 段里最大 60.5 MiB）。默认 16 MiB，超过的消息改走 zmq，慢一截。我们用 256：原片的交接时间降到 0.59–0.65 倍，首字等待快 2–4%。代价是共享内存约 10 × 这个值：256 时广播环实测 2.5 GiB，比默认（按公式 10 × 16 MiB = 160 MiB，没实测）多约 2.34 GiB |
| 视觉塔分块的 `M2_VC_DEVICE` | 就用这张卡（只有一张可见卡时，本插件自动设成 `cuda:0`） | 必须显式设一张有余量的卡 |
| 给视觉塔分块留显存 | `--gpu-memory-utilization` 要给它留出空间，否则会和 KV cache 抢。Qwen3.8 的视觉塔实测最多 3.0 GiB；小模型的视觉塔小得多，按视觉塔参数量 × 2 字节估，再加激活 | 同左，只算放视觉塔的那一张 |

### GPU：为什么默认不用 GPU 解码

vLLM 自带两种 GPU 解码：pynvvideocodec（`--media-io-kwargs '{"video":{"backend":"pynvvideocodec"}}'`，NVDEC 解完把帧拷回主机）和 torchcodec cuda（`{"backend":"torchcodec","device":"cuda"}`，帧留在显存里）。我们都测过，默认不推荐：

- **pynvvideocodec 比原生 OpenCV 快，但比切段解码慢**：服务里实测，解码那一步降到原生 OpenCV 的 0.26–0.80（短片 0.26，原片各组 0.69–0.80），>30 分钟组首字等待降到 0.74 倍；可插件仍比它快 1.10–3.80 倍（见结果表 2）。它和切段解码不能同时用（切段解码只接管 OpenCV 路径）。解码器上下文约占 1.25 GiB 显存。
- **pynvvideocodec 会改像素**：解出的像素和 OpenCV 不同，我们的视频里最多差 17 个灰度。它的 `hw_decoders` 只是给并发请求分路，不会把一段视频拆开并行解。
- **torchcodec cuda 在显存被占满时会 OOM**：帧留在显存里，我们在 `--gpu-memory-utilization 0.85` 下，一段 305 s 的视频要 1.6 GiB，直接失败。它也会改像素。
- **可以试的情况**：不要求逐位相同、CPU 很紧、GPU 有余量（torchcodec cuda 还要显存余量能放下整段视频的帧）时，可以试 pynvvideocodec。

### GPU：硬件限制

- NVIDIA 驱动 ≥ 580：torch 2.13.0+cu130 需要 CUDA 13。
- 视觉塔 FP8 注意力（`--mm-encoder-attn-dtype fp8`）在 SM120（RTX 50 系）上起不来：cuDNN 9.20 的"FP8 输入、bf16 输出"注意力内核只给 SM100 提供，vLLM 的检查只看计算能力 ≥ 10.0，所以会放行，然后在建图时失败。SM100 上可能可以，我们没测过。视觉塔分块也不支持 FP8 注意力。
- probe 会输出每张卡的型号、显存和计算能力。

## 结果（8×RTX 5090，Qwen3.8-Flash-Next，在线 FP8，TEP8）

**口径**：只量首字等待（从发出请求到收到第一个 token），单请求，回答截在 16 个 token。插件只动第一个 token 之前的步骤，所以首字等待的数字和回答长短无关；整个请求快几倍，要看回答有多长，生成那一段没变快。

### 3. 正确性

- 不改输出的那几项：全量 908 段视频（MV-Bench-mini 878 段 + Video-MME 原片 30 段）逐位相同；500 次长跑没有泄漏，句柄、线程数不涨；4 并发、8 并发和串行逐位相同；边界视频（奇数宽高、旋转、可变帧率、坏码流等）1155 条测过。
- 坏码流上，被错误隐藏补出来的帧，像素可能和 vLLM 不同：vLLM 自己在不同线程数下也不固定。结构（帧数、下标、形状）保持一致，坏 GOP 以外的帧逐位相同。
- 会改输出的两项（视觉塔每卡一整份、视觉塔分块）考了精度，见下面一节。

#### 精度（会改输出的两项）

**哪些要考、为什么**
- 不改输出的四项（`exact` 预设：切段解码、跳帧、去拷贝、边解码边缩放）送进视觉塔的输入和 vLLM 逐位相同，模型看到的东西没变，不用考。
- 会改输出的只有两项，都改的是视觉塔的输出：
  - vLLM 自带的"视觉塔每卡一整份"（`--mm-encoder-tp-mode data`）：和默认的跨卡切分比，视觉塔输出相对差中位 6.2%。
  - 本插件的"视觉塔分块"（`M2_VISION_CHUNK=1`）：和每卡一整份比，100 段里 34 段逐位相同，其余 66 段相对差中位 2.9%、最大 6.25%。
- 这两个差都不只是末位舍入，所以要用考题看它们会不会改答案。

**考法**
- 题库：990 道视频选择题，MV-Bench-mini 900 道，加 Video-MME 的本地子集 90 道。用固定种子 20261025 分成 10 组，每组 50 道（45 道 MV-Bench + 5 道 Video-MME），组和组之间不重复。"视觉塔每卡一整份"考了全部 10 组，500 道；"视觉塔分块"考了前 5 组，250 道。
- 生成：EvalScope 1.14.0 的 `general_vmcq`，提示词要求一步步想，最后一行写 `ANSWER: 字母`。温度 0、top_p 1、seed 0、`max_tokens` 1024、关思考，一次只发一道题。
- 抽答案：取回答里最后一个 `ANSWER:` 后面的字母，不分大小写。没有这个标记时，取最后一个大写字母，它必须是这道题的选项之一，否则记为没给出答案（`evalscope/utils/multi_choices.py:255` 解析，兜底在 `:190`）。
- 判分：抽出的字母等于标准答案算对，否则算错。没给出答案也算错。
- 检验：只看两边对错不同的题，用双侧精确 McNemar 检验。
- 和谁比：基线是最朴素的服务（vLLM 0.31.0 + 在线 FP8，默认设置，不装插件）。每一项都和同一段时间里考的基线比，题目完全相同，并且确认过两边送进视觉塔的输入逐位相同，差别只在视觉塔。"视觉塔分块"那组开着另外三个插件、12 线程和视觉塔每卡一整份，并且开了严格模式。
- 基线自己会差多少：温度 0、种子固定，答案也不是每次都一样。同一个服务实例上把第 1 组考两遍，两遍有 3 题对错不同（31 对和 32 对）。换一个服务实例重考前 5 组，250 题里有 23 题对错互换（前对后错 12、前错后对 11），答对数 171 对 170。拿两项和基线比时，以这个波动为尺子。
- 坏输出：查了三类：空回答；乱码或连续重复的字符；写满 1024 个 token、还没写出答案。

|---|---|---|---|---|---|---|---|---|---|
| 视觉塔每卡一整份（vLLM 自带） | 500 | 343（68.6%） | 344（68.8%） | 30 | 31 | 1.0 | 0 | 0 | 44（49） |

- 两边所有没给出答案的题，都是写满了 1024 个 token、还没写到 `ANSWER:`，没有一道是格式错乱。

## 高并发（推断，未测）

这一节是按代码和单请求的实测推断的。我们只测过并发下结果和串行逐位相同、不卡死：不改输出的四项测过 4 并发和 8 并发，视觉塔分块只测过 4 并发（24 个请求）。没测过并发吞吐。高并发部署上线前请自己压测。

### 插件对吞吐的影响

- **切段解码不减少总解码量**：它把一个请求的解码分给多个核同时做。高并发时，vLLM 原生也会同时解好几个请求，把 CPU 占满，两边最后都卡在 CPU 总量上。插件多出来的活是每段从前一个关键帧开始的重复解码和进程间通信，省下的是跳帧少解的非参考帧。所以满载吞吐估计和原生差不多，首字等待的优势会随并发升高而缩小。切段请求平均约 31 CPU 核秒（按长度 12–57），可以拿这个数和自己的核数估算 CPU 那一侧的上限。
- **视觉塔两边都排队**：不开插件时，实测视觉塔也是一个请求接一个请求地算（4 个请求同时到，视觉塔分别在 2.68、4.62、5.96、7.31 s 开始）。开了视觉塔分块，那份视觉塔固定在 API 进程、`M2_VC_DEVICE` 那一张卡上，还要和那张卡上的语言模型抢算力。高并发下是插件这边先堵还是原生那边先堵，没测过。
- **单个 API 进程会抢 GIL**：解码调度、缩放切块线程、视觉塔都在同一个 Python 进程里。短片上解码多出的约 11 ms，推断就是这么来的（没用 profiler 坐实）。并发越高越明显。

### 多开 API 进程（`--api-server-count`）

- **实测：单开它，对首字等待几乎没用**。测法是不开插件，4 个请求同时到，用的是同一段 26 秒、1080p、抽 52 帧的短视频，3 轮取中位。开 4 个 API 进程以后，缩放切块基本不排队了：12 个请求里 11 个在发出后约 0.4 s 就开始。可首字等待几乎没变：第 4 个请求只从 8.84 s 变成 8.67 s，第 1 个反而从 3.65 s 慢到 4.62 s。
- **原因**：后面还是只有一个引擎在调度，视觉塔和预填充照样排队，瓶颈从 CPU 挪到了 GPU。
- **和插件一起用没测过**。按代码推断，每个 API 进程有自己的 GIL，能减少上面说的 GIL 争抢，但同样解决不了 GPU 那一侧的排队。
- **和插件一起用时要注意**：
  - 每个 API 进程各有一个切段进程池。`M2_SEG_N × M2_SEG_THREADS × 进程数` 要按上面"按机器选参数"的规则一起算，不要每个进程都用默认的 16 × 4。
  - 每个进程池常驻内存中位约 0.85–1.0 GiB，最多约 2.6 GiB，要乘以进程数。
  - `M2_VC_DEVICE` 只能填一张卡，多个 API 进程的视觉塔会都放到这同一张卡上，每份约 3 GiB 显存。

### 建议

- 低并发、在意首字等待：全部开（`all` 预设）。
- 高并发、在意吞吐：开切段解码、跳帧和去掉多余拷贝；不开视觉塔分块，视觉塔用 `--mm-encoder-tp-mode data`，由各卡各放一整份。
- 边解码边缩放：不改输出，可以开；但它每个请求在 API 进程里多起一个缩放切块线程，高并发下会和别的请求抢 CPU 和 GIL，收益可能变小（推断，没测过）。
- 多开 API 进程：单开实测对首字等待几乎没用；和插件一起用没测过。真要开，进程池的段数按进程数分下来。
- 真正的上限是 GPU 上的预填充，插件管不到。

## 版本和限制

- 目前只支持 vLLM 0.31.0、transformers 5.17.0、opencv-python-headless 5.0.0.93。插件替换的是这些库的内部函数，vLLM 或 transformers 版本不对时会打一行警告、不加载；opencv 版本不对时，跳帧那条路会自动关掉。
- torch 2.13.0+cu130 不放在依赖里：请按 PyTorch 官网装 cu130 版，再装本包。
- 只在一台 8×RTX 5090 上测过。换一台机器，尤其是核少的机器，收益会不一样。
- 只测了单请求的首字等待，没测高并发吞吐（4/8 并发只验了结果逐位相同、不卡死）。高并发怎么配见上文[高并发](#高并发推断未测)，那一节是推断。
- 短片首字等待的大头在预填充（语言模型自己在 GPU 上算），插件省得少。
- 跳帧只对含 B 帧或非参考帧的视频有用；只有 I、P 帧的视频，自动走原来的路径。
- 不支持 `--mm-processor-cache-gb > 0` 时的流水线（见上文"什么时候别开"）。

## 插件版本

- `m2_seg_decode`（含帧缓冲后台释放）、`m2_copyfree_resize`：和服务内测速用的版本逐字节相同。
- `m2_vision_chunk`：服务内测速用的版本（哈希见 `VENDORED.sha256`），之后只加了一处 `_tower_weight_files`（提交 d50d776）：模型目录里没有 `model.safetensors.index.json` 时，改为从单个 `model.safetensors` 读视觉塔权重（Qwen3-VL-2B 这类小模型）；有分片索引时读到的文件和验证过的版本相同。在 Qwen3-VL-2B 上跑 selfcheck，`off` / `exact` / `all` 全部 PASS，送进视觉塔的输入逐位相同。和考精度的那一版不同，差别只在状态字段，以及给计时打点留像素的那几行，算视觉塔的部分没动。服务内另外核过：100 段视频送进视觉塔的输入和上一行（不开视觉塔分块）逐段相同。
- `m2_pipe_resize`：多了 `M2_PIPE_RESIZE_THREADS` 开关。结果表测的是没有这个开关的版本；不设开关时计算路径和那一版完全相同，只多了一个只读的线程数记录（独立核查逐行读过 diff）。设了开关时验收通过：串行（五档各 36 条和不设逐位相同；全量 908 段两遍逐段相同；计时 15 段 × 5 档 75/75 逐位相同，线程数每档都等于设定值）；4 并发、8 并发各 3 轮，8 段原片和单块内联 + 流水线混合两组各 36/36 逐位相同，每个请求的缩放线程数都等于设定值，没有串到别的请求。
